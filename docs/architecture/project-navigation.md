# Project navigation (#27)

Tabs are grouped by **project = (profile, folder)**: `src/app/project-nav.js` (`window.OMP_PROJECT_NAV`, regression `test-project-nav.mjs`) is the single definition, shared by the tab bar (flat: one item per conversation, rendered by `design/chrome.jsx`; consecutive same-project tabs are marked `.tab-same-project`), the sidebar (`design/project-sidebar.jsx`), the history panel's per-project filter chips (`sessionProjects`, #35 — saved sessions are already one profile's, so the folder alone is the key) and `live.js`'s focus-existing lookups. Paths compare via `normPath` (slashes, trailing slash, case only for Windows drive/UNC paths); pathless tabs never group.

- **Working section** (sidebar, a segmented tab next to "open"): the sidebar's project list area has two views — "open" (all tabs grouped by project, the default) and "working" (non-idle tabs sorted by attention priority: waiting → failed → retrying → running → background). `src/app/working-surface.js` (`window.OMP_WORKING_SURFACE`, regression `test-working-surface.mjs`) filters and sorts; the view choice persists in localStorage. The working tab shows a count badge so the user sees activity without switching. Each working row has a tone-colored status dot and badge (accent/amber/rose/muted) and activates its tab on click. `desktop.working.next`/`prev` (`ctrl+alt+j`/`k`) cycle the working list globally regardless of which view is shown. State comes from the existing per-tab `runState` field (`turn-status.js` via `live.js`), never a second tracker.

- **Tab bar presentation.** The bar is flat: every open conversation is its own tab (`design/chrome.jsx`'s `TabBar` maps `projects` directly), so a project's tabs never fold into a chip. A tab shows the folder icon, `TabLabel`'s `folder · title` (#46), its run dot, a hover × (#45) that closes exactly that conversation, middle-click close and double-click rename. Consecutive tabs of the same project (same path and profile) take `.tab-same-project`: a 2px project-colour seam (`--tab-seam`, `chrome.css`) replaces the repeated folder icon, which the markup drops. `TabLabel`/`TabRunDot` come from `design/ui/tab-bits.jsx`, shared with the sidebar's rows and the composer's background-job note; `tabLabel` derives the prefix, never part of the renameable `name`.
- **Member order.** The sidebar's expanded rows list members in reverse registry order (`membersNewestFirst`, #38), so a newly opened conversation comes first. Display only: `sessionRegistry` keeps opening order (or the dragged one, below), which `groupTarget`, `open-tabs.json` restore and `closeSession`'s next-active choice read.
- **Saved conversations in the sidebar.** An expanded project also lists its saved sessions not already open (`OMP_PROJECT_NAV.savedForProject`: rows of the active profile's `listSavedSessions` whose `cwd` is the group's folder, minus any tab's `sessionFile`), newest first, capped at three rows with an "all N conversations…" row that opens the history modal preselected on the folder. A single-tab project with saved sessions gets a chevron for this; its expanded list has no member row, which would duplicate the project's own row. `app-live.jsx` refetches the list when the sidebar shows, the profile or tab count changes, or a turn starts or ends. The history modal's `initialCwd` — the active tab's folder from the tab bar's history button and `/history`, the group's folder from the "all …" row — preselects its project chip, falling back to "all" when the folder has none.
- **Reorder (#40).** Drag a tab anywhere along the bar, a project along the sidebar, or a conversation within its project in the sidebar; `Ctrl+Shift+PageUp`/`PageDown` (`desktop.tab.moveLeft`/`moveRight`) move the active tab's project one place. The bar's drag list (`projects`) is keyed by tab id, and `OMP_PROJECT_NAV.moveTab(tabs, id, targetId, after)` computes a flat drop anywhere in the bar — a tab lands wherever it is dropped, since the bar no longer has to keep a project's tabs contiguous. The sidebar keeps its project moves: `moveGroup` (list `projects`, keyed by group key) and `moveMember` (list `members:<key>`) keep every project contiguous there, which `groupTabs` renders, and `shiftGroup`/`groupKey` serve the keyboard move. `handleReorder` in `app-live.jsx` sends the bar's `projects` list through `moveTab`; the sidebar keeps `moveGroup` for its project blocks and `moveMember` for its rows. `OMP_BRIDGE.reorderTabs(ids)` rebuilds `sessionRegistry` in that order, applying only an exact permutation of the open tabs (a stale snapshot is a no-op); `notify` then persists it to `open-tabs.json`, so the order survives a restart. A sidebar member drop is in display order, the registry's reverse: a drop above a row is a registry move behind it. Since the registry order is the order, a dragged member to the top of a list is also what `findProjectTab` picks, and `closeSession` hands focus to the registry's last tab as before.
- **Drag mechanics** (`design/ui/use-drag-reorder.js`, geometry `app/drag-reorder.js`): pointer events, not HTML5 drag and drop — chosen while Tauri's native file drop (`dragDropEnabled`) still swallowed HTML5 drag events on Windows; it is off since the composer's image drop (#50), and pointer events stay for the threshold, Escape and capture. Items carry `data-reorder-list/-id/-axis`; only items of the pressed one's list are targets, so a sidebar member never lands among the sidebar's project rows. A press becomes a drag after 5 px, so a click still selects; the click a drop produces is swallowed, Escape cancels, and the pointer is captured on the item. Controls inside an item (×, rename, an inline input) never start a drag. `.tabs` is outside `.chrome`, so a tab drag never reaches the window-drag handler.
- **Project row context menu** (desktop only): right-clicking a sidebar project row (`onContextMenu` in `design/project-sidebar.jsx`, bubbling `(group, x, y)`) opens `design/project-menu.jsx` at the app root (`app-live.jsx` owns the state) with two rows from the pure `src/app/project-menu.js` (`window.OMP_PROJECT_MENU`, regression `test-project-menu.mjs`): reveal the folder in the OS file manager — label named per platform ("Reveal in Finder" / "Reveal in File Explorer" / "Open in File Manager", VS Code's vocabulary) and served by the Rust `reveal_project_path` command (`external_open::reveal_dir`: absolute-path + existing-directory validation before any spawn, then `open::that_detached` under `spawn_gate::shared()`, the `open_config_folder` pattern) — and copy the absolute path through the webview clipboard (`copyText`). Both rows grey out for a pathless group; both actions resolve true/false so the row flashes its outcome ("Copied" / "Copy failed") instead of closing silently on a denied clipboard or a vanished folder. The phone drawer never receives `onProjectMenu`, so a long-press there stays a text selection.

- Recent projects live in `<app config>/recent-projects.json` (`src-tauri/src/recent_projects.rs`), one list keyed per entry by profile, capped at 20 per profile, newest first. Disposable data: an unreadable file reads as empty and the next write replaces it; entries whose folder is gone are hidden, not deleted. Without an app config folder the list lives in memory for the app run (no temp-dir fallback, see `session-model.md`). `recent_projects_touch` canonicalises (`external_open::canonical_folder`), and so does `open_project`'s folder picker — tab paths and recent entries must be in the same form, or a folder picked through a symlink would not match its open tab.
- `live.js` records a recent only after a successful spawn (`_startProjectSession`, and a profile switch's respawn), and keeps `recentProjects` for the *active* profile only (`_syncRecentsProfile` on activation, last-tab close, profile refresh). All recents IPC runs through one queue (`_recentsCall`): the backend's `list` is unlocked, so unordered calls could let a stale list overwrite a newer touch.
- `openSession`/`+`/`Ctrl+T` always spawn. `openProject` (a recent row) and `resumeSession` focus an existing tab first (`findProjectTab` / `findConversationTab`). The latter matches the registry's `sessionFile`, seeded with the resume path and refreshed from `get_state` while the tab is active; `/new` and a profile respawn clear it (`_freshConversationFields`).
